# 1. Project Vision

Aegis is an autonomous SRE control plane designed to improve the reliability of APIs deployed through **WSO2 API Manager and Kubernetes**.

The fundamental question Aegis should answer is:

> **"Are my APIs healthy, why are they becoming unhealthy, and what can the platform automatically do about it?"**

The core reliability loop is:

```text
OBSERVE
   ↓
DETECT
   ↓
DIAGNOSE
   ↓
DECIDE
   ↓
REMEDIATE
   ↓
VERIFY
   ↓
OBSERVE
```

Aegis should eventually be capable of:

- monitoring API health
- measuring SLIs
- evaluating SLOs
- tracking error budgets
- detecting abnormal behaviour
- correlating metrics, logs, traces and deployment events
- identifying likely causes of incidents
- recommending remediation
- automatically performing safe remediation
- verifying whether remediation succeeded
- rolling back or escalating when remediation fails
- protecting the system from unsafe automated actions

# PHASE 3 — SLI / SLO / Error Budget Engine

Goal:

Turn raw telemetry into SRE concepts.

Example:

```yaml
api: payment-api

slo:
  availability:
    target: 99.9%

  latency:
    p95:
      target: 500ms

  error_rate:
    target: 1%
```

Aegis should calculate:

- availability
- latency
- error rate
- SLO compliance
- error-budget consumption

Success criteria:

Aegis can determine whether an API is violating its SLO and calculate its remaining error budget.

---

# PHASE 4 — Incident Detection

Goal:

Automatically detect reliability problems.

Detect scenarios such as:

- high error rate
- high latency
- pod crashes
- high CPU
- high memory
- traffic spikes
- backend unavailable

The detection engine should generate structured incidents.

Example:

```text
Incident ID: INC-001

API: payment-api

Severity: HIGH

Problem:
Error rate exceeded SLO threshold.

Detected:
10:42:31

Current error rate:
18.4%

SLO:
< 1%
```

Success criteria:

Aegis detects predefined reliability failures automatically.

---

# PHASE 5 — Canary Deployment & Safe Delivery

Goal:

Introduce progressive delivery.

Implement:

```text
v1
 │
 ├── 90% traffic
 │
 ▼
v2
 │
 └── 10% traffic
```

Monitor:

- error rate
- latency
- availability

If v2 performs poorly:

```text
v2
 ↓
Problem detected
 ↓
Traffic reduced
 ↓
Rollback
```

Success criteria:

Aegis can detect a problematic deployment and prevent it from becoming a full production failure.

---

# PHASE 6 — Automated Rollback

Goal:

Automatically rollback deployments when reliability conditions are violated.

Example:

```text
Deployment v2
     ↓
Error rate increases
     ↓
SLO violated
     ↓
Aegis evaluates policy
     ↓
Rollback
     ↓
Recovery verification
```

Important:

Rollback must be policy-driven.

Do not hard-code individual scenarios.

Success criteria:

A deliberately faulty deployment can be automatically rolled back and recovery can be verified.

---

# PHASE 7 — Automated Remediation Engine

Goal:

Allow Aegis to perform safe operational actions.

Possible actions:

- restart unhealthy workload
- scale replicas
- rollback deployment
- redirect traffic
- failover
- temporarily disable problematic deployment

Create a policy engine.

Example:

```yaml
policy:
  name: high-error-rate

  condition:
    metric: api_error_rate
    operator: ">"
    threshold: 10%

  duration: 2m

  action:
    type: rollback

  verification:
    error_rate: "< 2%"
```

Success criteria:

Aegis can select and execute predefined remediation actions based on policies.

---

# PHASE 8 — Safety Controller

Goal:

Prevent autonomous remediation from causing additional damage.

Before executing an action, Aegis should evaluate:

- Is the action allowed?
- Is the API affected?
- Is the action inside its permitted scope?
- Is a cooldown active?
- Has this action already failed?
- Is human approval required?
- Is the potential blast radius acceptable?

Possible execution modes:

```text
OBSERVE
    ↓
RECOMMEND
    ↓
AUTO-REMEDIATE
    ↓
AUTONOMOUS
```

Success criteria:

Aegis can safely decide whether an action should be automatically executed or escalated to a human.

---

# PHASE 9 — Root Cause Analysis

Goal:

Determine likely causes of incidents.

Do not attempt to solve every possible failure.

Initially support a defined set of scenarios:

- resource saturation
- application crash
- database unavailable
- network failure
- problematic deployment
- traffic overload

Use:

- metrics
- logs
- traces
- Kubernetes events
- deployment history
- dependency information

Example:

```text
Deployment occurred
        +
Error rate increased
        +
Latency increased
        +
Only new pods affected
        ↓
Likely cause:
Deployment regression
```

Success criteria:

For predefined failure scenarios, Aegis identifies the most likely cause with evidence.

---

Goal:

Validate whether Aegis actually improves reliability.

Introduce controlled failures such as:
